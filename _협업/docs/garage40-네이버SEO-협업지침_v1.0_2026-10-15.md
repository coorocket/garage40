## 1. 역할 나누기

| 구분 | 사장님 (운영) | 개발 담당 (Claude Code / 담당자) |
|---|---|---|
| 계정 | 네이버·구글 계정 만들기, 로그인, 결제 | 계정에 직접 로그인하지 않는다. 필요한 값(ID)만 받는다 |
| 사실 | 차종·시공 내용·가격·고객 동의 여부 확인 | 받은 사실을 문장·페이지로 만든다. **받지 않은 사실은 만들지 않는다** |
| 사진 | 전·중·후 촬영, 원본 전달 | 용량 줄이기(webp), alt 작성, 번호판 가림 확인 요청 |
| 결정 | 구축 계획 10장 ①~⑥, 판정(계속/수정/중단) | 선택지와 추천안을 정리해서 묻는다 |
| 코드 | 보지 않아도 된다. 화면과 숫자만 확인 | 수정·테스트·배포 |
| 숫자 | 매주 화요일 "실제 문의 수" 기록 | 서치어드바이저·GA4 수치 정리, 변화 해석 |

**원칙:** 사장님은 "무엇을 팔고 어떤 차를 어떻게 고쳤는지"를 책임지고, 개발은 "그것이 네이버에 어떻게 보이는지"를 책임진다.

## 3. 자료를 주실 때의 형식

### 3-1. 시공사례 1건 (4단계의 재료)

사장님은 아래를 **한 건에 한 묶음**으로 보내 주세요. 빈칸이 있으면 "모름"이라고 적어 주시면 됩니다.

```
차종/연식/색상:
고객 지역(동 단위까지, 동의 받은 범위):
증상(스월마크·홀로그램·오렌지필 등):
적용 프로그램(스탠다드/BEST/VIP):
소요 시간 / 투입 인원 / 폴리싱 단계 수:
비용(범위로 적어도 됨):
장인 메모(무엇을 보고 어떻게 판단했는지 2~3줄):
고객 동의: 있음 / 없음
사진: 전 2장 이상, 과정 1장, 후 2장 이상
```

### 3-2. 사진 규칙

- 휴대폰 원본 그대로 보낸다 (카톡 "원본 보내기" 또는 드라이브 폴더). 카톡 일반 전송은 화질이 줄어든다.
- 파일 이름은 `날짜_차종_전1.jpg`, `날짜_차종_후1.jpg` 형식. 폴더도 건별로 나눈다.
- 같은 조명 위치, 같은 각도로 전·후를 찍는다.
- 번호판은 가린 사본을 쓴다. 가림은 개발이 하되, 사장님이 최종 확인한다.
- **한 사진을 여러 사례에 쓰지 않는다.** 그 차의 실제 사진만 쓴다.
- 스톡·AI 생성 이미지는 사례에 쓰지 않는다.

### 3-3. 개발이 사장님께 묻는 형식

질문은 항상 **선택지 + 추천 + 기한**으로 보낸다. 예:

> 홈 title을 `GARAGE40 | 시흥 자동차광택·도장면 복원 40년`으로 확정해도 될까요? 확정 후 6주간 못 바꿉니다. (추천: 확정 / 대안: 지역명 추가) — 10/17까지

## 4. 작업 → 확인 → 배포 흐름

1. **작업 요청**: 사장님이 채팅으로 요청하거나 자료를 보낸다.
2. **개발 작업**: 작업 브랜치에서 수정하고 로컬에서 `pnpm build`로 확인한다.
3. **보고**: PR을 열고 아래 3가지를 쉬운 말로 적는다.
   - 무엇을 바꿨나 (파일이 아니라 "화면에서 무엇이 달라지는지")
   - 사장님이 직접 확인할 것 (휴대폰에서 어떤 버튼을 누르면 되는지)
   - 되돌리는 방법
4. **사장님 확인**: "확인했습니다" 또는 수정 요청. 수정 요청은 1건씩 번호를 붙여 준다.
5. **머지·배포**: 사장님 확인 후 `main`에 머지한다. Netlify가 자동 배포한다.
6. **수집 요청**: 새 페이지는 개발이 URL 목록을 만들고, 사장님이 서치어드바이저 "웹 페이지 수집"에 넣는다 (하루 최대 50건).

**머지 전 개발이 반드시 확인하는 것:** 빌드 성공, 새 페이지의 title·H1·canonical·description·스키마, 문의 버튼 3종(전화·카톡·문자) 동작, 모바일 화면 깨짐 없음.

## 5. 지켜야 할 규칙

| 규칙 | 내용 | 어기면 |
|---|---|---|
| 동결 | 배포한 title·H1·스키마는 **판정일(12/1)까지 변경 금지.** 급하면 "메모"로 남기고 판정 때 반영 | 6주 측정이 무효가 됨 |
| 변경 기록 | title·H1을 바꿀 때는 날짜·이전·이후를 시트 "변경 기록" 탭에 적는다 | 원인 추적 불가 |
| 정본 먼저 | 키워드 정본표(`docs/keyword-canonical.csv`)가 비어 있으면 5·6단계 페이지를 만들지 않는다 | 제목을 나중에 바꿔야 함 |
| 검색량 30 | 월 검색수 30 미만 키워드는 페이지로 만들지 않는다 | 아무도 안 치는 페이지 |
| 사실만 | 사장님이 준 사실만 쓴다. 가격·시간·차종·고객 정보를 추측해서 채우지 않는다 | 신뢰와 법적 문제 |
| 고객 정보 | 이름·번호판·상세 주소는 공개하지 않는다. 동 단위까지, 동의 범위 안에서 | 개인정보 문제 |
| 링크 방향 | 사례 → 아이템 → 카테고리 → 홈. 아이템 → 지역, 지역 ↔ 지역 링크 금지 | 구조 신호 훼손 |
| 복사 금지 | 지역명만 바꾼 복사 문단 금지. 지역 페이지는 해당 지역 사례 요약으로 차별화 | 구글 역효과 |
| 가격 공개 | 가격을 숨기지 않는다 | 이탈 증가 |
| 비밀값 | 계정 비밀번호·인증 코드는 채팅과 저장소에 쓰지 않는다. 측정 ID(`G-`)는 공개돼도 된다 | 계정 탈취 |

## 6. 개발 쪽 작업 규칙 (저장소)

- 작업은 전용 브랜치에서 한다. `main`에 직접 올리지 않는다.
- 커밋 메시지는 한국어로 "무엇을 왜"를 한 줄로 쓴다. 예) `feat: GA4 측정 코드와 문의 클릭 이벤트 추가`
- PR 1개 = 계획 단계 1개를 원칙으로 한다 (1단계, 2단계는 따로). 되돌리기 쉽게 하려는 것이다.
- 새 페이지는 계획 11-1의 뼈대를 따른다. `<body data-page-type="…">` 누락 금지.
- 대규모 구조 변경(3단계 `vite.config.js`·템플릿·생성 스크립트)은 작업 전에 방식 (가)/(나) 중 무엇인지 사장님께 한 줄로 확인한다. 추천은 (가).
- 문서(`docs/`)는 파일명에 버전·날짜를 붙이고, 내용을 바꾸면 새 버전으로 올린다 (`v1.1`).

## 7. 주간 리듬

| 요일 | 누가 | 무엇을 |
|---|---|---|
| 월 | 개발 | 이번 주 작업 목록 공유 (3줄 이내) |
| 매주 **화** | 사장님 + 개발 | 구축 계획 11-3의 10분 루틴. 사장님은 **실제 문의 수**를 시트에 기록, 개발은 노출·클릭·순위·`contact_click`을 기록 |
| 수~목 | 사장님 | 사례 자료·사진 전달, 확인 요청 건 답변 |
| 금 | 개발 | 이번 주 배포 요약과 다음 주 필요 자료 요청 |
| 매일 | 사장님 | 시공 때 전·중·후 사진 촬영 (주 2~3대면 충분) |

**답변 기한:** 개발이 건 질문은 영업일 2일 안에 답을 주시면 일정이 유지됩니다. 답이 없으면 추천안으로 진행하지 않고, **일정만 밀고 한 번 더 알립니다.** (단, 되돌릴 수 있는 작업은 추천안으로 진행할 수 있다고 사전에 합의한 경우에 한함.)

## 8. 문제가 생겼을 때

| 상황 | 먼저 할 일 | 연락 |
|---|---|---|
| 사이트가 안 열리거나 문의 버튼이 안 눌림 | 개발이 직전 배포를 되돌린다 (Netlify 이전 배포로 복원 또는 PR 되돌리기) | 사장님이 즉시 알림 |
| 서치어드바이저에 경고·오류 | 화면 캡처를 보낸다 | 당일 확인 |
| 고객이 사진 삭제를 요청 | 해당 사례의 사진·문구를 즉시 내리고 사이트맵·RSS에서도 뺀다 | 사장님이 개발에 전달 |
| 순위가 갑자기 떨어짐 | **title을 바꾸지 않는다.** 원인 기록부터 하고 판정 때 결정 | 개발이 보고서에 메모 |
| 자료가 부족해 사례를 못 만듦 | 부족 항목을 목록으로 돌려보낸다. 추측해서 채우지 않는다 | 개발 → 사장님 |
